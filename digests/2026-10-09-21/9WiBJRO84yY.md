## خلاصه

شرح می‌گوید ساختن هارنس ایجنت از صفر سنگین است و app server همان پروتکلی است که هارنس Codex را می‌پوشاند. گفتار با دست بلند کردن شروع شد و قول حدود هجده دقیقه داد. app server را پروتکل دور هارنس Codex خواند، نزدیک به agent client protocol، با این فرق که روی تکه‌های خود هارنس کنترل بیشتری می‌دهد و ACP را عام‌تر دانست. هارنس و app server را متن‌باز گفت، لایسنس Apache 2، قابل فورک. مدل دیگر را تا وقتی responses API سازگار داشته باشد وصل‌شدنی دانست، با تنظیم راحت برای LM Studio و Ollama.

پروتکل را JSON-RPC دانست که اپ Codex، افزونهٔ IDE، افزونهٔ VS Code، و کلاینت‌های سوم را راه می‌اندازد. Xcode، IDEهای JetBrains، و پروژه‌های متن‌بازی که «Theos T3 Code» و Remote X شنیده شد. گفت اوایل امسال با همین app server، Codex را داخل «Cloud Code» گذاشتند تا از آنجا بازبینی کند یا کار را به Codex بسپارد. کلاینت پیام می‌فرستد و رویداد می‌گیرد. به‌جای پیام فرضی، بازرس خودش را ساخت که رویداد واقعی بین اپ Codex و app server را می‌گیرد. نخ، پیکربندی، خواندن تنظیم، دلتای استریم، جست‌وجوی فایل، و تغییر فایل را رد و بدل همین پروتکل دانست. گفت بیش از ۱۲۰ پیام کلاینت دارند و هنوز اضافه می‌کنند: مقداردهی، نخ و نوبت، گذاشتن goal، فهرست پلاگین، جست‌وجو و تغییر فایل.

ورود با ChatGPT را بخشی از پروتکل دانست تا کاربر اپ سوم اشتراک خودش را بیاورد و مصرف از سقف Codex همان حساب برود. T3 Code را مثال همین مسیر گفت.

دو اهرم سفارشی‌سازی: developer instructions که به system prompt کدکس اضافه می‌شود، نه این‌که جایگزینش شود. گفت پرامپت سیستم داخل مخزن قابل دیدن است و توصیه این است که اضافه کنی تا میزان‌سازی مدل‌ها بماند. مثالش خود اپ Codex است که نسبت به افزونهٔ IDE یا CLI چیزهای خاص خودش را اضافه می‌کند. دوم، dynamic tools: تابع اضافه، با امکان deferred loading تا به‌جای تزریق در system prompt، Codex با tool search پیدایشان کند. جزئیات tool search را به جلسهٔ فردا حواله داد. روی هر نخ هم می‌شود مدل‌دهنده، مدل، و سندباکس را عوض کرد: کدام شبکه، کدام فایل.

app server داخل همان باینری Codex CLI است. اپ Codex باینری را داخل باندل خودش دارد و با هر نسخهٔ اپ عوض می‌شود. روی ویندوز دو باینری می‌فرستند: کامپایل لینوکس برای حالت WSL، و باینری ویندوز. گفت برای همان نسخه می‌توانی bindings تایپ‌اسکریپت یا JSON schema بسازی، چون پروتکل بین نسخه‌ها عوض می‌شود و برای همین باید باینری را با اپ خودت بفرستی، نه این‌که به CLI نصب‌شدهٔ کاربر تکیه کنی. حمل را STDIO یا وب‌سوکت گفت. Python SDK را به‌تازگی دوباره منتشرشده خواند که چرخهٔ عمر و ورود با ChatGPT را ساده می‌کند. راه دوم را پرسیدن از خود Codex دانست. مثال زد کلاینت Visual Basic را عمدتاً یک‌شات ساخته.

دمو: حدود یک ماه پیش خواسته Codex داخل Doom باشد، نه Doom داخل Codex. اپ Electron، رندر Wasm دومِ Cloudflare، بیشتر موتور به زبان C، بازی FreeDoom، و فایلی که گفته Codex عوضش کرده تا متن داخل خود موتور بازی کشیده شود. ارتباط با app server از IPC الکترون. مدل را ۵٫۵ گفت. ابزار داینامیک زره و سلامت، و سلاح‌ها با مهمات، را صدا زد. پرسید دایرکتوری چیست. Zsh مسیر جاری را داد و گفت ورک‌اسپیس مال خودش است، پس می‌شود از داخل بازی هم کد نوشت. اضافه کرد این را توصیه نمی‌کند و اپ Codex کمی بهتر است.

codex exec را رابط غیرتعاملی برای اسکریپت دانست، مناسب CI، مثل درست کردن خودکار یک PR. app server را برای کلاینت کامل، نشان دادن ایجنت، یا چند نخ هم‌زمان: هارنس eval، یا slash goal. گفت آنجا لازم نیست خودت فراخوان‌های exec را موازی کنی. رویداد thread تازه می‌فرستی.

سه نکتهٔ آخر: باینری هارنس را خودت بفرست تا شکست نسخه و عقب ماندن آپدیت کاربر گردن تو نیفتد. تابع تازه را در رابط بیاور و deferred کن تا پنجره را پر نکند. اگر دستور را عوض می‌کنی از developer instructions شروع کن. بازنویسی پرامپت پایه وسوسه‌انگیز است، ولی گفت پرامپت باید in distribution بماند و اگر از نو بنویسی آن کار از دست می‌رود.

## نکته‌های کلیدی

- بیش از ۱۲۰ پیام کلاینت. کنترل مدل و سندباکس per thread
- پرامپت پایه را عوض نکن. developer instructions را اضافه کن. ابزار اضافه را deferred کن
- باینری را با اپ بفرست. روی ویندوز دو باینری است: لینوکس برای WSL و native
- exec برای یک کار اسکریپتی است. چند نخ را با حلقهٔ exec نساز
- دموی Doom هنوز app server روی ماشین است. Zsh مسیر را برگرداند. خودش نوشتن کد آنجا را توصیه نکرد
