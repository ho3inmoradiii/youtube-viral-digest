# Sharing data between Micro Frontends

- **عنوان:** Sharing data between Micro Frontends | Cross Micro Frontend communication
- **لینک:** https://www.youtube.com/watch?v=JDTQ1N3kaOU
- **کانال:** Akash Ingole
- **بازدید:** ۱۲٬۱۶۶
- **موضوع:** Microfrontend shared state routing

## خلاصه

آکاش روی همان پروژه Module Federation قبلی‌اش نشان می‌دهد چطور یک میکروفرانت متن صفحه میزبان را عوض کند. دو پوشه mf1 و mf2 هست؛ mf2 روی localhost:3002 داخل کانتینر میزبان سوار است. سناریو: داخل ریموت یک ورودی و دکمه submit داری و انتظار داری عنوان «product listing» در host به متن تایپ‌شده عوض شود.

دو راه را نام می‌برد. راه اول API است: ریموت POST می‌کند، host با GET همان داده را می‌خواند. راه دوم، که کدش را می‌زند، رویداد سفارشی است. در submit یک `CustomEvent` با نام `change-text` و payload داخل `detail` ساخته و dispatch می‌شود. host در `useEffect` به همان نام گوش می‌دهد، `event.detail` را در state می‌ریزد، و متن را عوض می‌کند. قرارداد به‌اندازه یک رشته نام رویداد و یک آبجکت detail است.

بخش پایانی مرز استفاده را می‌کشد. runtime و remoteEntry.js وقتی به درد می‌خورد که یک تیم کل یک مسیر را مالک باشد؛ مثلاً تیم دیگر کل صفحه کارت فروشگاه را بدهد. برای کامپوننت‌های کوچک روی همان صفحه، پکیج build-time و npm مناسب‌تر است. دلیل عملکردی هم دارد: اگر ویجت runtime چهار بار روی صفحه بیاید و هر کدام API خودش را بزند، چهار درخواست تکراری داری.

## نکات کلیدی

- CustomEvent یک قرارداد سبک است: نام رویداد به‌علاوه detail. نیازی به کتابخانه state مشترک نیست.
- API زمانی منطقی است که داده باید بماند یا چند مصرف‌کننده ناهم‌زمان آن را بخوانند.
- مسیر کامل مال تیم دیگر = runtime. دکمه و کارت کوچک = پکیج build-time.
- تکرار ویجت runtime می‌تواند درخواست شبکه را ضرب کند. این را قبل از «استقلال» حساب کن.
- دمو آموزشی است؛ نسخه، احراز هویت رویداد، و namespace رویداد در تولید باید صریح باشد.

## برش کوتاه

> برای صفحه اصلی و کارت فروش که تیم دوم کل مسیر را می‌دهد، runtime خوب است. برای چند کامپوننت کوچک نه؛ پکیج build-time. وگرنه چهار نمونه از یک ویجت یعنی چهار بار API.
