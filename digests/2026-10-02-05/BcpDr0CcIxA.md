# Micro front-end architecture at Walmart

- **عنوان:** Micro front-end architecture at Walmart
- **لینک:** https://www.youtube.com/watch?v=BcpDr0CcIxA
- **کانال:** Hasgeek TV
- **بازدید:** ۳٬۴۰۴
- **موضوع:** Micro Frontends production case study

## خلاصه

نادیا از Walmart Labs بنگلور درباره تجربه کشف در walmart.com حرف می‌زند: صفحه خانه، جست‌وجو، مرور، و صفحه محصول. حدود ۷۰ مهندس بین آمریکا و هند، هم‌زمان حدود ۱۰ ابتکار، حدود ۱۰ کتابخانه شخص ثالث و ۱۰ کتابخانه داخلی مشترک، و تقریباً ۵۰۰۰ بازدید صفحه در دقیقه. ویجت «آیا این قطعه به ماشین من می‌خورد؟» فقط برای لوازم خودرو حدود ۱۲۰ فایل و نزدیک به ۶۰۰۰ خط کد اضافه است، چون باید برگشت کالا را کم کند.

درد واقعی قبل از معماری، بازبینی است. ریویوئر روز الزاماً روی همان ابتکار کار نمی‌کند، پس به جنبه فنی نگاه می‌کند نه رفتاری. PR دو تا سه روز معطل می‌ماند. تعریف عملی آن‌ها از میکروفرانت یک فرگمنت قابل استفاده مجدد است که هم کلاینت هم سرور رندر شود، حدود ۸۰ درصد چرخه عمر مستقل داشته باشد، و رفتارش را از context میزبان بگیرد. بودجه عملکرد (TTFB، اولین رسم معنی‌دار، و متریک سفارشی بالای صفحه) قرارداد است، نه آرزو.

code splitting و React Loadable باندل را تکه‌تکه می‌کنند ولی چرخه عمر، نسخه، و اجرای مستقل نمی‌دهند. پس فرگمنت باید کم‌حجم باشد، نسخه فریم‌ورک میزبان را دوباره دانلود نکند (React 15 میزبان و React 16 فرگمنت یعنی دو بار React)، و با چند خط یکپارچه شود. پیاده‌سازی: اسکلت داخل یک ماژول Node، پرچم A/B، لود تنبل JS و CSS، API مستقل، تست مستقل، پیکربندی JSON، و ارتباط فقط با postal.js روی کانال و تاپیک، نه دستکاری DOM میزبان. کتابخانه‌های مشترک با Webpack DLL در یک مانیفست قفل می‌شوند.

نتیجه: زمان برگشت PR کمتر شد، تست A/B داخل خود فرگمنت ماند، و باگ‌فیکس فرگمنت دیگر رگرسیون کامل صفحه میزبان نمی‌خواست. هزینه: فرگمنت یتیم می‌شود اگر مورد استفاده بعدی را پوشش ندهد، و سرویس جدا یعنی زیرساخت اضافه. اسلاید پایانی به نوشته مارتین فاولر درباره میکروفرانت ارجاع می‌دهد.

## نکات کلیدی

- این معماری برای ۷۰ نفر و ۵۰۰۰ بازدید در دقیقه است، نه برای تیم چهارنفره.
- سود اصلی چرخه عمر مستقل است: ریویو کوتاه‌تر و رگرسیون محلی. اگر این درد را نداری، فرگمنت نساز.
- اشتراک نسخه فریم‌ورک بودجه عملکرد است. دو React روی کلاینت یعنی شکست همان SLO که بهانه‌ات بود.
- ارتباط با رویداد (اینجا postal.js) مرز را حفظ می‌کند؛ خواندن DOM میزبان یعنی فرگمنت دیگر مستقل نیست.
- فرگمنت یتیم و هزینه زیرساخت را از روز اول در محاسبه بیاور.

## برش کوتاه

> code splitting به تو نمی‌گوید چطور نسخه‌گذاری کنی یا جدا دیپلوی کنی. باگ‌فیکس فرگمنت دیگر نباید رگرسیون کل صفحه میزبان بخواهد. و اگر جدا هاستش کنی، هزینه زیرساخت را هم پذیرفته‌ای.
