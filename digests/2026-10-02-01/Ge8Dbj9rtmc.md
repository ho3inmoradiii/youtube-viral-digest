## خلاصه

این گفت‌وگو میکروفرانت‌اند را همان ایدهٔ میکروسرویس می‌داند که به رابط کاربر رسیده است: به‌جای یک کدبیس درهم، تکه‌های خودبسنده که تیم‌ها جدا مالک و مستقر می‌کنند، در حالی که کاربر یک سایت یکپارچه می‌بیند. درد مونولیت این است که حتی یک اصلاح کوچک CSS در فوتر می‌تواند لانچ یک قابلیت بزرگ را پشت یک پایپلاین استقرار نگه دارد. انگیزهٔ اصلی خودمختاری تیم است؛ تیم تسویه‌حساب بدون جلسه با تیم کاتالوگ منتشر می‌کند. شعاع انفجار کوچک‌تر است و سازمان می‌تواند موازی رشد کند، به شرطی که هر تکه یک برش عمودی از سرویس بک‌اند تا UI خودش باشد.

اصولی که منابع روی آن تأکید دارند همان اصول میکروسرویس است. مسئولیت واحد یعنی مثلاً فقط ویجت ورود یا نمای سبد. اتصال سست یعنی وابستگی عمیق به داخل یکدیگر نباشد و تعامل از رابط پایدار بگذرد: پیام، گذرگاه رویداد، یا درگاه API مشترک. انسجام بالا یعنی منطق و استایل و مارکاپ همان قابلیت داخل همان واحد بماند. این الگو پیش‌فرض هر پروژه‌ای نیست. اپ کوچک با چند صفحه با مونولیت ساده‌تر است. یک تیم کوچک هم از خودمختاری چیزی گیرش نمی‌آید. جایش وقتی است که اپ بزرگ و چندتیمی است، یا باید از Angular.js قدیمی تکه‌تکه به React یا Vue بروید بدون بازنویسی یکباره. مقیاس‌پذیری بار کاربر بیشتر به معماری بک‌اند برمی‌گردد تا خود این الگو.

ترکیب سمت سرور با پروکسی معکوس یا درگاه، مسیرهایی مثل پروفایل و تسویه‌حساب را به اپ‌های بک‌اند جدا می‌فرستد و تکه‌های HTML را قبل از مرورگر به هم می‌دوزد. استقرار مستقل می‌شود، اما رفتن بین بخش‌ها اغلب رفرش کامل صفحه است و حس SPA از بین می‌رود. هدر و فوتر و ناوبری هم ممکن است در هر اپ سروری تکرار شوند. iframe روش قدیمی است و برای تکهٔ قدیمی یا ویجت شخص ثالث مثل حباب پشتیبانی یا پیش‌بینی آب‌وهوا جدا و قابل استقرار است، ولی برای UI اصلی توصیه نمی‌شود. هر iframe وابستگی خودش را می‌آورد و مثلاً React را دوباره لود می‌کند. ارتباط با postMessage سخت است، چیدمان و تغییر اندازه و سیاست cross-origin و دسترس‌پذیری و سئو دردسرند. جز جایی که جداسازی سنگین برای محتوای نامطمئن لازم است، معمولاً بیش از آن‌که حل کنند مسئله می‌سازند.

بستهٔ npm در زمان بیلد برای دکمه و توکن طراحی و ابزار و استایل مشترک خوب است، اما استقرار مستقل نیست. با عوض شدن بسته، میزبان باید نسخه را در package.json بالا ببرد، دوباره بیلد کند و کل اپ را منتشر کند. این اتصال وقتی مطلوب است که کنترل نسخه و عرضهٔ کنترل‌شدهٔ دیزاین‌سیستم را بخواهید. Module Federation ترکیب را به زمان اجرا می‌برد. مثالش ویجت مقاله‌های مرتبط در یک وبلاگ است که روی سرور یا دامنهٔ دیگر است؛ میزبان با اسکرول کاربر، جاوااسکریپت را می‌گیرد و بدون رفرش و بدون iframe نشان می‌دهد. ریموت ماژول را expose می‌کند، میزبان remoteEntry.js را مثل مانیفست می‌شناسد و تقریباً مثل فایل محلی ایمپورت می‌کند. پلاگین Webpack یا ابزار مشابه سیم‌کشی را انجام می‌دهد. بخش shared حیاتی است: اگر میزبان React 18 را دارد و ریموت هم همان را می‌خواهد، نسخهٔ میزبان استفاده می‌شود نه دانلود دوباره. اگر نسخه‌ها ناسازگار باشند می‌توان بالاترین نسخهٔ سازگار را گرفت، هشدار داد، یا در نهایت چند نسخه لود کرد که برای کارایی باید از آن پرهیز کرد.

single-spa بیشتر ارکستر است تا مکانیزم لود. چند اپ با فریم‌ورک‌های مختلف، React و Angular و Vue و Svelte، را بر اساس URL سوار و پیاده می‌کند. اگر همه‌چیز React باشد، منبع می‌گوید احتمالاً لازم نیست و Module Federation کافی است. خود single-spa کد را لود نمی‌کند؛ system.js، ایمپورت، یا اغلب Module Federation زیرش است. در مقایسه، استقرار مستقل مال Module Federation است؛ ترکیب سرور معمولاً به مسیر URL بسته است؛ iframe از نظر فنی مستقل است؛ بازندهٔ این محور بستهٔ زمان بیلد است. کارایی Module Federation با اشتراک وابستگی و حس SPA بهتر است. ترکیب سرور با رفرش کامل کندتر حس می‌شود. iframe به‌خاطر بارگذاری ایزوله و تکرار منبع عموماً ضعیف است. بسته اگر external و peer درست باشد می‌تواند خوب باشد، ولی خطر تکرار و باندل اولیهٔ بزرگ هست. راه افتادن Module Federation شیب یادگیری و تخصص باندلر می‌خواهد. iframe اول آسان و بعد در لبه سخت است. بسته فرایند انتشار و رجیستری خصوصی می‌خواهد که برای خیلی تیم‌ها آشناتر است. احراز هویت در Module Federation معمولاً داخل زمینهٔ میزبان است: توکن را پایین بدهید یا کوکی نشست را بفرستید، و اگر دامنه فرق دارد باید CORS و ارسال credential و ویژگی SameSite درست باشد. ترکیب سرور اغلب به سرویس مرکزی یا نشست درگاه تکیه می‌کند. احراز هویت بین دامنه‌ها با iframe سخت است و اغلب از آن پرهیز می‌شود. بسته چون بخشی از میزبان است همان سازوکار میزبان را دارد. در توسعهٔ محلی می‌توان میزبان را روی ماشین گذاشت و ریموت را از محیط استیجینگ یا پورت دیگر گرفت؛ این از شبیه‌سازی ترکیب سمت سرور، دردسرهای iframe، و npm link یا yarn link سرراست‌تر است.

پیچیدگی واقعی بعد از راه افتادن شروع می‌شود. CSS سراسری خطرناک است و باید CSS Modules، styled-components، Shadow DOM یا قراردادهایی مثل BEM با محدودهٔ مشخص باشد. میزبانی رایج، ذخیرهٔ ابری مثل S3 است چون ارزان و قابل اتکا و مقیاس‌پذیر است، به شرط کش بلند برای چانک‌ها با نام فایل و کش خیلی کوتاه یا بدون کش برای remoteEntry.js تا به‌روزرسانی دیده شود. ردیابی خطا بین میزبان و چند ریموت و سرویس بک‌اند مشاهده‌پذیری را سخت می‌کند و ردیابی توزیع‌شده مهم می‌شود. حرف زدن با رویداد سفارشی است، مثلاً سبد رویداد به‌روزرسانی می‌فرستد و هدر تعداد را گوش می‌دهد. اشتراک Redux یا Zustand ممکن است ولی اتصال را زیاد می‌کند. راه غیرمستقیم، API بک‌اند یا گذرگاه پیام است. الگوی BFF طبیعی درمی‌آید: تیم جزئیات محصول فقط دادهٔ محصول و نظر را برای UI خودش شکل می‌دهد. بعد درگاه API، JWT یکدست، و استراتژی واکشی لازم می‌شود. تست لایه‌لایه است: واحد، یکپارچگی با BFF، انتها‌به‌انتها روی چند میکروفرانت‌اند که شکننده‌تر است، و تست قرارداد روی API و رویداد. امنیت ایزولاسیون کامل iframe نیست؛ HTTPS، توکن، اعتبارسنجی ورودی و دفاع در عمق لازم است تا نفوذ به یک تکه کل اپ و همهٔ دادهٔ کاربر را باز نکند.

اسپاتیفای در کلاینت دسکتاپ، که عمدتاً فناوری وب است، بخش‌هایی مثل پلیر، کتابخانه، جست‌وجو، فید کشف و فعالیت دوستان را طوری جدا کرده که تیم پلیر جدا از تیم نمای کتابخانه تکرار کند. IKEA این رویکرد را در شکستن مونولیت تجارت الکترونیک برای تکرار سریع‌تر روی سفر مشتری، مثلاً فهرست محصول و تسویه‌حساب، و تجربهٔ یکدست‌تر وب و موبایل به کار برده است. جمع‌بندی این است که راه واحدی نیست: ساختار تیم، پشتهٔ موجود، میزان استقلال واقعی و نوع تجربهٔ کاربر تصمیم را می‌سازند. سؤال آخر هماهنگی است؛ استاندارد مشترک و ارتباط تازه لازم است تا انسجام بصری، کارایی و مسیر منطقی کاربر حفظ شود وقتی تیم‌ها بخش‌های یک صفحه را در زمان‌های مختلف منتشر می‌کنند. فناوری، به‌خصوص Module Federation و آنچه حول نسخهٔ ۲ مطرح است، هنوز در حال تکامل توصیف می‌شود.

## نکات کلیدی

- میکروفرانت‌اند برای خودمختاری تیم و شعاع انفجار کوچک‌تر است، نه برای اپ کوچک یا تیم تک‌نفره.
- ترکیب سرور استقرار مسیری مستقل می‌دهد ولی اغلب رفرش کامل و تکرار هدر و فوتر دارد.
- iframe برای ویجت نامطمئن شخص ثالث قابل دفاع است و برای پوستهٔ اصلی اپ به‌خاطر کارایی، postMessage، چیدمان، سئو و دسترس‌پذیری توصیه نمی‌شود.
- بستهٔ npm نسخه را صریح کنترل می‌کند و استقرار را به میزبان گره می‌زند؛ برای دیزاین‌سیستم مناسب است.
- Module Federation در زمان اجرا با remoteEntry و اشتراک وابستگی، حس SPA و استقرار مستقل را با هم هدف می‌گیرد.
- single-spa چرخهٔ عمر چند فریم‌ورک را مدیریت می‌کند و اگر همه React باشند مزیت اصلی‌اش کم می‌شود.
- درد عملیاتی CORS، تداخل CSS، کش remoteEntry، ردیابی توزیع‌شده، BFF، تست قرارداد و امنیت بین تکه‌هاست.
- اسپاتیفای و IKEA نمونه‌های مقیاس سازمانی‌اند: بخش‌های جدا با تیم‌های جدا، نه معیار عددی یک معماری واحد.

## برش‌های مهم

- یک اصلاح CSS در فوتر نباید لانچ قابلیت تیم دیگر را پشت یک استقرار واحد نگه دارد.
- iframe برای هستهٔ اپ معمولاً بیش از مسئله‌ای که حل می‌کند درد می‌سازد؛ جایش محتوای شخص ثالث ایزوله است.
- اگر میزبان React را لود کرده، ریموت سازگار نباید نسخهٔ دوم را دانلود کند.
- remoteEntry باید کش کوتاه داشته باشد و بقیهٔ چانک‌ها می‌توانند کش بلند با نام فایل داشته باشند.
