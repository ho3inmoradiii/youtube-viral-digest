## خلاصه

جان این قسمت را بعد از حرف‌های قبلی‌اش دربارهٔ معماری‌های مبتنی بر MACH و سیستم‌های headless می‌گذارد و سراغ یک الگوی پیاده‌سازی می‌رود: Backend for Frontend یا BFF. اول با شوخی اسم را از best friend forever جدا می‌کند و بعد تعریف را از یک مشکل واقعی می‌سازد.

اگر فرانت را روی میکروسرویس‌ها و بیشتر از یک سیستم headless بسازی، الگوی ساده نقطه-به-نقطه است: هر وقت به یک API نیاز داشتی همان را از داخل خود اپ صدا بزنی. برای اپ ساده این قابل‌قبول است. در اپ پیچیده‌تر چند دردسر پیدا می‌شود. فرانت باید چیزهای زیادی از بک‌اند و APIهایش بفهمد؛ اضافه یا عوض کردن API یک میکروسرویس یعنی تغییر کد فرانت، عوض کردن API یک فروشنده سخت می‌شود، و در نهایت باید نسخهٔ تازه‌ای از اپ منتشر شود. دادهٔ برگشتی هم اغلب همان شکلی نیست که رابط لازم دارد. مثال دیدن سبد این است: اول API سبد را صدا می‌زنی و شاید فقط مجموعه‌ای از شناسه‌ها برگردد. بعد برای هر شناسه API محصول را می‌زنی و حجم زیادی اطلاعات محصول می‌گیری، در حالی که فقط شناسه، نام، قیمت و شاید یک تصویر بندانگشتی لازم بوده. پس هر فرانت باید کد و منطق اضافه برای ترجمهٔ داده داشته باشد و قبل از رسیدن به شکل نهایی، چندین صدا را هماهنگ کند. اگر این کار از لایهٔ نمایش جدا نشود، فرانت‌ها پیچیده‌تر و سخت‌نگهداری می‌شوند. این را تشدید می‌کند که هر فرانت نیاز متفاوتی دارد: اپ صوتی با فروشگاه وب یکی نیست، و اپ دستیار مشتری داخل فروشگاه با اپی که خود مشتری استفاده می‌کند فرق دارد. از نظر فنی هم تعداد زیاد صداها در مدل نقطه-به-نقطه می‌تواند کارایی را اذیت کند، به‌خصوص در اپ‌های مرورگری.

BFF را یک API سفارشی می‌داند که بین APIهای میکروسرویس و اپ فرانت می‌نشیند. فرانت به‌جای اینکه مسئول صدا زدن همهٔ میکروسرویس‌ها و پردازش نتیجه‌ها باشد، یک صدا به BFF خودش می‌زند. آن API سفارشی میکروسرویس‌های مربوط را صدا می‌کند، پاسخ‌ها را ساختار و قالب می‌دهد و نتیجهٔ مرتب را برمی‌گرداند. پیچیدگی فرانت کم می‌شود. BFF نقش یک رابط ساده را دارد و فقط روی یک رابط کاربری تمرکز می‌کند، نه بیشتر. فرانت ساده‌تر و سبک‌تر می‌ماند، نیاز فرانت از دغدغه‌های بک‌اند جدا می‌شود، و اپ کمتر از ساختار API خبر دارد، پس در برابر تغییر API مقاوم‌تر است.

خطای سرور برای فرانت بی‌معنی است، ولی BFF می‌تواند آن را به چیزی تبدیل کند که برای کاربر معنی دارد و تجربه را بهتر کند. اطلاعات حساسی که ممکن است از صدا زدن میکروسرویس برگردد را هم می‌تواند پنهان کند و داده‌ای که لازم نیست را حذف کند؛ این را یک لایهٔ امنیت اضافه می‌داند. توسعه هم راحت‌تر بین تیم‌ها جدا می‌شود، چون تیم فرانت مسئول BFF است، کنترل بیشتری روی نحوهٔ مصرف API دارد و وابستگی‌اش به تیم توسعهٔ API کمتر می‌شود. ممکن است به نظر برسد یک گام شبکهٔ اضافه تأخیر را زیاد کرده و کارایی را پایین آورده، اما با BFF می‌شود صداها را هوشمندانه به‌صورت دسته‌ای به میکروسرویس‌ها زد و مجموعهٔ کوتاه‌تر و قالب‌خورده‌تری به تجربهٔ کاربر برگرداند.

چیزهایی که باید از آن‌ها پرهیز کرد را هم فهرست می‌کند. API خودبسنده را داخل BFF نساز؛ آن APIها باید در لایهٔ API بمانند. BFF فقط لایهٔ ترجمه است و API جدید نمی‌سازد. از تکرار هم دوری کن. BFF برای یک اپلیکیشن است، نه برای یک نوع دستگاه. مثلاً تجربهٔ یک اپ روایی روی iOS و Android تقریباً یکی است، پس باید یک BFF برای خود اپ داشته باشی، نه یکی برای اندروید و یکی برای iOS، چون منطق تقریباً همان است. زیاد به BFF تکیه نکن. قابلیت‌ها و امنیت باید در فرانت یا در APIها بمانند. BFF پرکنندهٔ فاصله است، نه جایی برای افزودن قابلیت یا سرویس جدید. می‌گوید این الگو برای پیاده‌سازی پلتفرم با معماری MACH و headless مفید است، ولی تنها الگو نیست. در ویدیوهای بعد به GraphQL و API gateway می‌رسد و برای جا افتادن همین الگو پیشنهاد می‌کند مجموعهٔ MACH را از بحث میکروسرویس شروع کنی.

## نکات کلیدی

- الگوی نقطه-به-نقطه برای اپ ساده قابل‌قبول است، ولی فرانت را به جزئیات API میکروسرویس‌ها گره می‌زند و عوض کردن فروشنده یا خود API را به انتشار نسخهٔ تازه وصل می‌کند.
- مثال سبد نشان می‌دهد برای چند شناسه باید جداگانه API محصول را صدا زد و کلی داده گرفت، در حالی که UI فقط شناسه، نام، قیمت و شاید تصویر کوچک می‌خواهد.
- هر فرانت منطق ترجمه و هماهنگی چند صدا را برای خودش تکرار می‌کند و نیازها هم فرق دارند: اپ صوتی، فروشگاه وب، دستیار داخل فروشگاه، و اپ خود مشتری یکی نیستند.
- BFF یک API سفارشی برای همان یک رابط است؛ فرانت یک صدا می‌زند و BFF صداهای میکروسرویس، قالب داده و پاسخ نهایی را جمع می‌کند.
- خطای خام سرور را به پیام قابل‌فهم برای کاربر تبدیل می‌کند، دادهٔ حساس را پنهان می‌کند و دادهٔ اضافی را حذف می‌کند.
- تیم فرانت مالک BFF می‌شود و کنترل مصرف API را از تیم API جدا می‌کند؛ گام اضافهٔ شبکه را با صداهای دسته‌ای و پاسخ کوتاه‌تر جبران می‌کند.
- BFF نباید API خودبسنده، قابلیت تازه یا امنیت اصلی را نگه دارد و برای iOS و Android یک اپ واحد نباید دو BFF جدا داشته باشد.

## برش‌های مهم

- فرانت به‌جای صدا زدن همهٔ میکروسرویس‌ها یک صدا به API سفارشی خودش می‌زند.
- خطای سرور برای فرانت بی‌معنی است و BFF باید آن را به چیزی قابل‌فهم برای کاربر تبدیل کند.
- BFF برای یک اپلیکیشن است، نه برای یک نوع دستگاه؛ iOS و Android همان اپ یک BFF می‌خواهند.
