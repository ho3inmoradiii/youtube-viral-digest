## خلاصه

جک هرینگتون پلاگین تازهٔ Module Federation برای Vite و Rollup را نشان می‌دهد که دو اپ مستقرشده بتوانند کد را در زمان اجرا با هم شریک شوند. مثالش صفحهٔ خانه و صفحهٔ جزئیات محصول است که هر دو هدر می‌خواهند. در اشتراک زمان بیلد، هدر داخل یک کتابخانه است و هر دو اپ آن را ایمپورت می‌کنند؛ برای عوض کردن هدر باید هر دو را دوباره مستقر کنید. در اشتراک زمان اجرا، خانه هدر را expose می‌کند و جزئیات محصول همان را پویا مصرف می‌کند، پس انتشار نسخهٔ جدید هدر بدون استقرار مجدد مصرف‌کننده به دستش می‌رسد. این را برد معماری برای شرکت‌های بزرگ با چند تیم و چند اپ می‌داند که تجربهٔ یکدست می‌خواهند ولی کامپوننت مشترک را همزمان به‌روز کنند. نقشهٔ ویدیو این است: فدراسیون بین دو اپ Vite، فروشگاه مشترک، سازگاری با Webpack که مبدأ Module Federation است، و در آخر مونوریپو برای مقایسهٔ زمان بیلد و زمان اجرا.

دمو با pnpm و قالب React است. اپ remote کامپوننت را بیرون می‌دهد و host آن را مصرف می‌کند؛ یک اپ می‌تواند هم‌زمان هر دو نقش را داشته باشد ولی این‌جا جدا هستند. پورت remote باید ثابت باشد، این‌جا ۵۰۰۱ با strict port، چون در غیر این صورت هر بار ۵۱۷۶ یا ۵۱۷۷ یا ۵۱۷۸ می‌شود و آدرس مانیفست می‌شکند. پورت host مهم نیست. دکمهٔ شمارنده عمداً هوک و state محلی دارد، چون فدراسیون ممکن است بدون هوک سالم به نظر برسد و با هوک بترکد: خطای چند نمونهٔ React وقتی دو اپ سر این‌که کدام React در زمان اجرا لود شود رقابت می‌کنند. هر دو طرف پلاگین را لازم دارند. در کانفیگ remote نام remoteApp، فایل remoteEntry، مسیر src/button و اشتراک react و react-dom ثبت می‌شود.

فرق Vite با دموی معمول Webpack این است که pnpm dev فایل remoteEntry را نمی‌سازد؛ باید build و بعد serve کنید. مانیفست در assets/remoteEntry.js می‌نشیند و کتابخانه‌های مشترک و خود دکمه را اعلام می‌کند. او تأکید می‌کند این فایل‌ها دارایی ایستا هستند و باید مثل CSS و تصویر روی چیزی مثل S3 بروند. اگر سرور اپی که کامپوننت را شریک کرده پایین بیاید، دارایی ایستا نباید پایین بیاید؛ اگر خود S3 پایین بیاید می‌گوید آن روز برای همه تعطیل است. host با کلید remoteApp به همان remoteEntry اشاره می‌کند و دکمه را با import معمولی از remoteApp/button می‌گیرد. اشتراک react و react-dom باعث می‌شود فدراسیون بین host و remote داوری کند و یک نسخه بماند، هم برای کارایی هم برای پایداری. host را با build و preview روی پورت ۴۱۷۳ بالا می‌آورد.

شمارندهٔ دو مرورگر یکی نیست: روی ۵۰۰۱ دکمه مثلاً روی ۷ و شمارندهٔ محلی روی ۴ است و روی host دکمه ۱۷ و شمارنده ۸. دلیلش این است که کد شریک می‌شود نه state. برای state مشترک باید سازوکار جدا داشت، مثالی که می‌زند Firebase است. بعد فقط CSS دکمه را در remote تیره می‌کند، فقط remote را دوباره می‌سازد و سرو می‌کند، و با رفرش host همان دکمهٔ تیره را می‌بیند بدون استقرار مجدد پورت ۴۱۷۳.

برای state بین host و میکروفرانت‌اند، مثل شناسهٔ کاربر، Recoil یا Jotai را توصیه می‌کند و Jotai را ترجیح می‌دهد. یک اتم count و هوک useCount شبیه useState در remote مشترک است، ولی host تا وقتی خود store expose نشود و jotai هم در فهرست share نباشد همان تعامل را نمی‌بیند. بعد از آن کلیک در هر دو جا یک شمارنده را جلو می‌برد و می‌گوید با همین سطح می‌شود شناسهٔ کاربر و سبد را روی اتم‌های مشترک گذاشت. دلیل پرهیز از Redux یا Zustand برای این مرز این است که state مشترک یعنی اتصال. سطح کوچک، مثل شناسه و محتوای سبد، قابل قبول است. در مدل اتمی برای پهن کردن سطح باید اتم تازه اضافه کنید؛ در Redux یا Zustand فروشگاه را بی‌اصطکاک بزرگ می‌کنید و اتصال سفت‌تر می‌شود.

سازگاری با Webpack 5 را با create-mf-app و اپ wp-host روی پورت ۸۰۸۰ امتحان می‌کند. آن اسکلت React 17 است و اپ‌های Vite روی 18.2 هستند، پس React را بالا می‌برد و Webpack CLI را به 4.10 می‌رساند و render قدیمی را به createRoot از react-dom/client عوض می‌کند. چون Vite روی ESM است، Webpack باید خروجی ماژول، هدف EcmaScript 2020، experiments.outputModule و یک index با script از نوع module داشته باشد و چیزی inject نکند. ایمپورت دکمه این‌جا default را از ماژول دکمه برمی‌دارد. بعد از این تنظیم‌ها همان دکمه از اپ Vite/Rollup داخل host مبتنی بر Webpack 5 دیده می‌شود.

بخش آخر مونوریپوی Turborepo به نام monorepo-version است با app-one و app-two. این‌جا host و remote معنی ندارند، چون اشتراک زمان اجرا نیست؛ هر دو دکمه را از بستهٔ UI و فروشگاه را از بستهٔ store داخل workspace می‌گیرند. مزیت زمان بیلد این است که TypeScript و تست واحد راحت‌اند و بعد از بیلد اپ یک بستهٔ منسجم است بدون وابستگی خارجی در زمان اجرا. عیبش نبود به‌روزرسانی پویا است. مزیت زمان اجرا این است که یک بار remote را منتشر می‌کنید و مصرف‌کننده‌ها بدون استقرار مجدد همان را می‌گیرند. عیب‌هایش جدی‌اند: با رفتن از TypeScript به جاوااسکریپت تایپ گم می‌شود، ماژول در زمان تست واحد در دسترس نیست، و ریسک زمان اجرا دارید؛ اپ دیگر می‌تواند کامپوننتی را که به آن وابسته‌اید طوری عوض کند که اپ شما بشکند و شما تا لحظهٔ اجرا خبردار نشوید، برخلاف خطای زمان بیلد. انتخاب را به همین موازنه واگذار می‌کند.

## نکات کلیدی

- اشتراک زمان بیلد یعنی به‌روزرسانی هدر هر دو اپ را دوباره مستقر می‌کند؛ زمان اجرا فقط منتشرکننده را.
- پورت remote باید ثابت بماند چون host به URL مانیفست remoteEntry وابسته است.
- در Vite فایل remoteEntry با dev ساخته نمی‌شود؛ build و سپس serve لازم است و خروجی دارایی ایستا است.
- فدراسیون کد را شریک می‌کند نه state؛ دو شمارندهٔ جدا طبیعی است مگر فروشگاه را هم expose کنید.
- react و react-dom باید share شوند وگرنه چند نمونهٔ React با هوک خطا می‌دهد.
- برای سطح مشترک کوچک Jotai یا Recoil را به فروشگاه قابل رشد Redux و Zustand ترجیح می‌دهد تا اتصال بی‌اصطکاک پهن نشود.
- Module Federation در Vite/Rollup با تنظیم خروجی ESM با host ساخته‌شده در Webpack 5 سازگار شد.
- مونوریپو TypeScript و تست و انسجام بیلد را ساده می‌کند و ریسک تغییر ناگهانی در زمان اجرا را برمی‌دارد.

## برش‌های مهم

- اگر اپی که کامپوننت را شریک کرده از کار بیفتد، دارایی ایستای روی S3 نباید با آن پایین بیاید.
- دیدن state متفاوت بین دو اپ باگ نیست؛ فقط کد مشترک است نه حافظهٔ مشترک.
- هرچه دادهٔ بیشتری بین host و میکروفرانت‌اند رد شود، اتصال سفت‌تر می‌شود.
- در زمان اجرا ممکن است کامپوننتی که به آن وابسته‌اید بشکند و تا لحظهٔ اجرا نفهمید؛ در زمان بیلد همان را موقع ساخت می‌بینید.
