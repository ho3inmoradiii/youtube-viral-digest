## خلاصه

IBM تفاوت API و MCP را برای عامل‌های زبانی باز می‌کند. تا پیش از این، وصل شدن مدل به داده و ابزار یعنی API. اواخر ۲۰۲۴ آنتروپیک Model Context Protocol را به‌عنوان استاندارد باز معرفی کرد. استعاره ویدیو USB-C است: میزبان چند کلاینت MCP دارد، هر کلاینت نشست JSON-RPC 2.0 باز می‌کند، و سرورها قابلیت‌ها را عرضه می‌کنند. لپ‌تاپ نقش host را دارد، پروتکل نقش درگاه، و درایو و مانیتور نقش سرور.

دو نیاز عامل را پوشش می‌دهد: context (سند، دانش، رکورد) و ابزار (جست‌وجو، سرویس، محاسبه). سه نخستین primitive: tools که اکشن با اسکیمای ورودی و خروجی‌اند، resources که داده فقط‌خواندنی‌اند، و قالب پرامپت. عامل در runtime فهرست را می‌پرسد (`tools/list` و بقیه) و بدون دیپلوی مجدد کد، قابلیت تازه را می‌بیند. خیلی از سرورها فعلاً فقط tools دارند.

API، به‌خصوص REST، قرارداد عمومی HTTP است: GET و POST و مسیرهایی مثل `/books/123`. هر سرویس مسیر و احراز هویت خودش را دارد، پس پنج API یعنی پنج آداپتور، و کشف قابلیت در runtime معمولاً نیست. MCP برای عامل طراحی شده و همه سرورها همان الگو را حرف می‌زنند. نکته پایانی که ویدیو رویش تأکید دارد: خیلی از سرورهای MCP در باطن همان API را صدا می‌زنند. سرور گیت‌هاب ابزار سطح بالا عرضه می‌کند و داخلش به REST گیت‌هاب ترجمه می‌کند. پس MCP رقیب API نیست؛ لایه سازگار با عامل روی شانه‌های API است.

## نکات کلیدی

- MCP استاندارد اتصال عامل به context و ابزار است، نه جایگزین همه‌کاره REST.
- کشف داینامیک یعنی عامل هر بار فهرست قابلیت را می‌گیرد؛ تغییر API سنتی معمولاً تغییر کد کلاینت می‌خواهد.
- tools و resources و prompts سه primitive پایه‌اند؛ همه سرورها هر سه را ندارند.
- پنج سرور MCP یک شکل صدا زده می‌شوند؛ پنج REST پنج قراردادند.
- پیاده‌سازی واقعی اغلب لفاف یک API موجود است.
- فایده مهندسی: یک بار پروتکل عامل را بنویس، اتصال سرویس‌ها را پشت سرور MCP عوض کن.

## برش کوتاه

> MCP و API حریف هم نیستند. سرور MCP اغلب همان REST را پشت یک کاتالوگ قابل کشف قایم می‌کند. عامل لازم نیست پنج قرارداد جدا را حفظ کند؛ انسان هنوز باید بداند آن پشت کدام API واقعاً صدا زده می‌شود.
