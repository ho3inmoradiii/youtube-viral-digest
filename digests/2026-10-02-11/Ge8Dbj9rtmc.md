## خلاصه

این ویدیو یک گفت‌وگوی توضیحی است، نه گزارش یک مهاجرت واقعی. انگیزه را از درد مونولیت فرانت می‌گیرد: یک اصلاح کوچک CSS در فوتر، لانچ فیچر بزرگ را نگه می‌دارد چون همه‌چیز یک خط لوله دیپلوی است. پاسخ پیشنهادی، مالکیت یک برش عمودی است؛ از سرویس بکند تا تکه UI همان تیم.

بعد روش‌ها را با معیار استقلال دیپلوی، کارایی، زحمت راه‌اندازی، و احراز هویت کنار هم می‌گذارد. ترکیب سمت سرور برای استقلال بر اساس ریشه URL خوب است ولی حس اپ سیال را کم می‌کند. iframe برای ویجت شخص ثالث یا بخش legacy به‌درد می‌خورد چون محتوا جدا دیپلوی می‌شود، اما same-origin، دسترس‌پذیری و SEO را سخت می‌کند و برای بدنه اصلی محصول توصیه نمی‌شود. پکیج npm در زمان build برای دیزاین‌سیستم رایج است، ولی میزبان تا نسخه package.json را عوض نکند و دوباره بیلد ندهد به‌روز نمی‌شود؛ دیپلوی‌ها به هم قفل می‌مانند.

Module Federation را نقطه مقابل build-time می‌داند: مرورگر قطعه را هنگام استفاده صفحه می‌گیرد، مثلاً ویجت مقاله‌های مرتبط از یک سرور دیگر. single-spa هم در مقایسه هست. هشدار پایانی درباره وابستگی، تصادم استایل، و مانیتور کردن تکه‌هاست و می‌گوید خود Module Federation هنوز در حال بالغ شدن است، از جمله بحث‌های نسل بعدی آن.

## نکات کلیدی

- درد کلاسیک مونولیت فرانت: یک تغییر کوچک، صف دیپلوی همه را بند می‌آورد.
- برش عمودی یعنی مالکیت از API تا UI، نه تکه‌کردن هدر و فوتر به ریپوهای جدا.
- iframe ایزوله سنگین است؛ برای بخش اصلی اپ معمولاً دردسرش بیشتر از سودش است.
- npm در build-time اشتراک کد را ساده می‌کند و انتشار را دوباره جفت می‌کند.
- Module Federation یکپارچگی را به runtime می‌برد تا مصرف‌کننده برای هر تغییر مشترک redeploy نشود.
- احراز هویت، نسخه وابستگی، و برخورد CSS هزینه‌های عملیاتی روش‌های مدرن‌اند نه جزئیات فرعی.

## برش کوتاه

> iframe برای چت شخص ثالث و قطعه legacy هنوز زنده است. برای ستون فقرات محصول خودت، اغلب مسئله را بیشتر می‌کند. اشتراک npm هم تا وقتی هر میزبان جداگانه نسخه را بالا نبرد، استقلال دیپلوی نیست.
