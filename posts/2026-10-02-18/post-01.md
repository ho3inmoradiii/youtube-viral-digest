# هارنس را عوض کن، نه پروتکل را

همه دارند مرگ MCP را اعلام می‌کنند.
پنجرهٔ کانتکست معمولاً از خود پروتکل پر نشده.

سرور تازه را که به ایجنت تیکت وصل کردیم، قبل از اولین سؤال مفید، فهرست ابزار همان اول داخل سشن ریخت. یکی گفت پروتکل تمام شده، برگردیم به اسکریپت خودمان. یان چورن امروز در AI Engineer همین موج را باز کرد. مشخصات MCP دربارهٔ شکل هارنس تقریباً هیچ نمی‌گوید. پیاده‌سازی اول ساده بود: ده سرور، نزدیک صد ابزار، و به گفتهٔ او گاهی حدود یک‌سوم پنجره پیش از شروع کار می‌رفت. نتیجهٔ هر ابزار دوباره به همان پنجره برمی‌گشت. دقت پایین، هزینه بالا. این را باگ هارنس نامید، نه نقص پروتکل.

ساب‌ایجنت فقط صورت‌حساب را جابه‌جا می‌کند. توکن سر جایش است و اگر ابزار رمز یا دادهٔ گنده برگرداند، هنوز داخل یک کانتکست نشسته. درمانی که واقعاً پنجره را خلوت می‌کند کشف تدریجی است؛ همان کاری که Claude با ابزار جست‌وجوی ابزار و بعد Cursor کرد. فقط چیزی را بیاور داخل که لازم است. Code Mode یک قدم آن‌طرف‌تر است: ابزار را تابع نبین، کد ببین. مدل کد و grep را از دادهٔ واقعی بلد است. صدا زدن ابزار را باید جدا به آن یاد بدهند.

CLI از اول همین‌طور کار می‌کند و برای همین حس بهتری دارد. جعبهٔ سیاه محلی است. برای دسترسی ریموت و لاگین، استانداردش MCP است. جمع‌بندی خود چورن این است که مسابقهٔ «CLI بهتر است یا MCP» غلط است. MCP به‌علاوهٔ یک CLI که پیچیدگی را پشت یک bash پنهان کند، همان چیزی است که ایجنت از قبل بلد است. eval اولیه‌شان هم همین را نشان داد: MCP خام گاهی تندتر تمام کرد و توکن بیشتری خورد. mcpc و CLI نزدیک هم بودند. خودش گفت این نمودارها هنوز زودند.

درس ساده است. قبل از اعلام مرگ پروتکل، ببین هارنست کاتالوگ را یکجا قورت می‌دهد یا اجازه می‌دهد ایجنت با grep پیدایش کند.

تو MCP را کنار گذاشتی، یا فقط کلاینتی را که همهٔ ابزار را همان اول لود می‌کرد؟
